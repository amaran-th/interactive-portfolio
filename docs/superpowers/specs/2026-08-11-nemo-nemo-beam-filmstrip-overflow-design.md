# 네모네모빔 프레임 필름스트립 세로 스크롤 제거

**목표:** 프레임 모드 하단 필름스트립(`FrameFilmstrip.tsx`)에서 각 프레임 카드의 내용이 컨테이너 높이보다 커서 생기는 세로 스크롤을 없앤다.

## 원인

각 프레임 카드(`w-16` 폭)는 4단으로 쌓여 있다: ①번호+눈 아이콘 헤더 줄, ②40px 썸네일, ③지속시간 입력, ④삭제 버튼. 실측 결과 이 스택의 실제 필요 높이는 91px인데, 컨테이너(`h-24`=96px에서 상하 패딩 `py-2`=16px를 뺀)가 줄 수 있는 높이는 79px뿐이다.

부모 스크롤 컨테이너(`overflow-x-auto`)는 가로축만 스크롤하려는 의도였지만, `overflow-y`를 따로 지정하지 않으면 브라우저가 CSS 스펙에 따라 `overflow-y`도 `auto`로 계산한다(한 축이 `visible`이 아니게 되면 다른 축도 `visible`로 남을 수 없다는 규칙) — 그 결과 의도치 않은 세로 스크롤바가 생긴다.

## 수정

### 카드 구조를 4단 → 3단으로

`FrameFilmstrip.tsx`의 프레임 카드 레이아웃을 바꾼다:

- **1단(헤더)**: 번호(왼쪽) + 눈 아이콘 + 삭제 버튼(오른쪽, 둘 다). 지금 따로 있던 삭제 버튼(4단)을 이 줄로 옮긴다 — 64px 카드 폭에 9px 텍스트 하나 + 12px 아이콘 둘을 나란히 놓기엔 충분하다.
- **2단**: 40px 썸네일(그대로).
- **3단**: 지속시간 입력(그대로).

삭제 버튼의 클릭 핸들러(`onClick`에서 `e.stopPropagation()` 후 `!isPlaying && onDelete(layer.id)`)와 `disabled`(재생 중이거나 프레임이 1장뿐일 때) 조건은 그대로 옮긴다 — 위치만 바뀐다.

### 안전 마진

3단으로 줄이면 계산상 필요 높이가 약 73px로 줄어 79px 여유 안에 들어오지만, 폰트 렌더링·서브픽셀 차이로 경계에서 다시 스크롤이 생길 위험이 있다. 카드의 상하 패딩을 `py-1`(4px×2)에서 `py-0.5`(2px×2)로 줄여 2px 정도 추가 여유를 둔다.

## 영향받지 않는 것

- 컨테이너 높이(`h-24`) — 캔버스 영역을 더 뺏지 않기 위해 그대로 둔다.
- 가로 스크롤(`overflow-x-auto`) — 프레임이 많을 때 옆으로 스크롤하는 동작은 그대로 유지한다.
- 정보량 — 번호·가시성 토글·썸네일·지속시간 편집·삭제 다섯 가지 전부 항상 보인다(사용자 확정 사항).
- 상호작용 모델 — 호버 전용 노출 없이 지금처럼 클릭 기반.
- 지속시간 인라인 편집(버퍼 후 커밋), 재생 중 편집 잠금 등 기존 로직 — 손대지 않는다.

## 테스트 계획

자동화된 테스트 스위트가 없는 프로젝트 — `npx tsc --noEmit`·`npm run lint`·`npm run build`로 정적 검증하고, 브라우저(Playwright 임시 스크립트)로 다음을 확인한다:

1. 프레임 모드로 전환한 뒤 필름스트립의 스크롤 컨테이너에서 `scrollHeight`가 `clientHeight`를 넘지 않는지(세로 스크롤이 실제로 사라졌는지) 확인한다.
2. 카드 안에 번호·눈 아이콘·삭제 버튼이 한 줄에 모두 보이는지, 삭제 버튼 클릭이 여전히 정상 동작하는지(재생 중이 아닐 때) 확인한다.
3. 프레임이 1장뿐일 때 삭제 버튼이 비활성화되는지, 재생 중일 때 삭제·눈 아이콘·지속시간 입력이 모두 비활성화되는지 확인한다(기존 동작 유지 확인).
4. 지속시간 입력에 포커스를 주고 값을 바꾼 뒤 blur하면 정상적으로 커밋되는지 확인한다(레이아웃 변경이 버퍼-커밋 로직에 영향 없는지).
5. 가로로 프레임을 여러 개(예: 10장) 만든 뒤에도 가로 스크롤은 정상 동작하고 세로 스크롤은 여전히 안 생기는지 확인한다.
