# GPU가 빠지면 지도가 회전을 멈춘다

회사에서 일정 각도로 회전 보정한 지도를 띄워야 했다. 그런데 어떤 환경에서는 지도가 회전하지 않았다. `map.setHeading()`을 호출해도 아무 일도 일어나지 않았다. 원인은 벡터(WebGL) 모드가 래스터로 폴백된 것이었다. 이걸 계기로 "왜 GPU 가속 유무가 회전 가능 여부라는 *기능* 차이로 이어지는가"를 파고들었다.

---

## 래스터 맵과 벡터 맵

지도를 화면에 그리는 방식은 크게 둘이다.

**래스터 맵**은 타일 서버가 미리 그려서 내려주는 정사각형 비트맵 타일의 모음이다. 각 타일은 화면 축에 정렬된 이미지다. 브라우저는 이 이미지들을 격자에 붙이기만 한다.

**벡터 맵**은 도로(선), 건물(폴리곤), 라벨(텍스트)을 *좌표 데이터(지오메트리)* 로 받아 클라이언트가 GPU로 직접 그린다. 구글맵에서는 벡터 활성화된 Map ID를 쓸 때 이 경로가 활성화된다.

핵심 차이는 "회전을 어디서 처리하느냐"다.

---

## 비트맵을 회전한다는 것

래스터 맵을 회전하려면 이미 그려진 비트맵을 돌려야 한다. 이게 왜 문제인지는 캔버스로 직접 해보면 바로 보인다.

```js
ctx.translate(W / 2, H / 2);
ctx.rotate(headingRad);
ctx.drawImage(tileBitmap, -side / 2, -side / 2, side, side);
```

비트맵 회전은 **픽셀 리샘플링**이다. 회전된 격자의 각 출력 픽셀이 원본 어디에서 왔는지를 보간으로 추정한다. 결과는 세 가지로 망가진다.

1. **흐려진다.** 얇은 도로 선과 텍스트가 보간을 거치며 뭉개진다.
2. **라벨이 같이 기울어진다.** 비트맵에는 "이건 글자"라는 정보가 없다. 90°에서 글자가 옆으로 눕고 180°에서 뒤집힌다.
3. **비용이 픽셀 수에 비례한다.** 매 프레임 전체 화면을 리샘플하므로 고해상도·고DPR에서 CPU가 무겁다.

그래서 구글맵의 래스터 렌더러는 회전을 *잘 못 하는* 게 아니라 **아예 제공하지 않는다**. heading과 tilt API가 동작하지 않는다. 내가 겪은 게 바로 이것이었다.

---

## 지오메트리를 회전한다는 것

벡터 맵은 비트맵이 아니라 좌표를 가지고 있다. 회전은 좌표에 회전 행렬을 곱하는 것뿐이다.

$$
\begin{bmatrix} x' \\ y' \end{bmatrix} =
\begin{bmatrix} \cos\theta & -\sin\theta \\ \sin\theta & \cos\theta \end{bmatrix}
\begin{bmatrix} x \\ y \end{bmatrix}
$$

이 곱을 GPU의 **버텍스 셰이더**에서 모든 정점에 대해 수행한다.

```glsl
uniform mat2 u_m;     // 회전·스케일 행렬
uniform vec2 u_half;  // 뷰포트 절반
in vec2 a_pos;        // 정점의 월드 좌표
void main() {
  vec2 s = u_m * a_pos;                                  // 회전 적용
  gl_Position = vec4(s.x / u_half.x, -s.y / u_half.y, 0.0, 1.0);
}
```

GPU는 수천 개 정점에 **같은 변환을 병렬로** 적용한다(SIMD). 그리고 변환된 좌표로부터 매 프레임 *다시 래스터화* 한다. 그래서:

- **어떤 각도에서도 선명하다.** 비트맵을 돌리는 게 아니라 도형을 그 각도로 새로 그린다.
- **사실상 공짜다.** 행렬 곱은 GPU가 가장 잘하는 일이고, 정점 수가 픽셀 수보다 훨씬 적다.

라벨은 한 가지 트릭이 더 있다. 텍스트까지 같이 회전하면 읽을 수 없으므로, **빌보드(billboard)** 로 처리한다. 마커의 *위치*만 회전 행렬로 옮기고, 글자 쿼드 자체는 회전시키지 않아 항상 수평을 유지한다.

```glsl
// 마커 위치만 회전, 코너 오프셋(px)은 회전 없이 더함 → 라벨은 늘 수평
vec2 s = u_m * a_marker + a_corner;
```

실험의 Example 1에서 두 패널을 나란히 돌려보면 이 차이가 한눈에 보인다. 왼쪽(래스터)은 흐려지고 라벨이 뒤집히고, 오른쪽(벡터)은 선명하고 라벨이 똑바로 선다.

## GPU 가속과 WebGL 파이프라인

벡터 회전이 공짜인 이유를 한 단계 더 내려가 보자.

**CPU**는 강력한 코어 몇 개로 순차 처리에 강하다. **GPU**는 약한 코어 수천 개로 같은 연산을 여러 데이터에 동시에 적용하는 데 강하다(SIMD). "모든 정점에 같은 행렬을 곱하기", "모든 픽셀에 같은 색 계산하기"는 GPU에 딱 맞는 작업이다.

WebGL 파이프라인은 이렇게 흐른다.

```
정점 버퍼 → [버텍스 셰이더] → 래스터화 → [프래그먼트 셰이더] → 프레임버퍼
            정점마다 변환                  픽셀마다 색
```

- **버텍스 셰이더**: 정점 좌표를 변환한다(모델·뷰·투영 행렬, 그리고 우리의 회전).
- **래스터화**: 삼각형을 픽셀로 채운다.
- **프래그먼트 셰이더**: 픽셀마다 색을 정한다(우리 실험에서는 마커 원의 안티앨리어싱, 라벨 텍스처 샘플링).

CSS의 "하드웨어 가속"도 같은 원리다. `transform`/`opacity`만 바뀌는 레이어는 브라우저가 GPU로 합성(composite)하므로 부드럽다. 지도 회전은 이 합성을 *콘텐츠 전체* 에 적용한 것이라고 볼 수 있다.

---

## 그래서 언제 래스터로 폴백되나

벡터 렌더링은 **WebGL2 + 벡터 Map ID** 가 둘 다 있어야 한다. WebGL을 못 쓰는 순간 래스터로 떨어진다.

- **GPU 블록리스트**: Chrome은 드라이버 버그가 알려진 GPU를 블록한다. 이 경우 WebGL이 SwiftShader(소프트웨어 렌더러)로 돌거나 비활성화된다.
- **하드웨어 가속 비활성**: 설정에서 끄거나, 원격 데스크톱·일부 가상화 환경.
- **GPU 없는 서버/헤드리스**: SSR·테스트 환경.
- **컨텍스트 한도 초과**: 브라우저는 동시 WebGL 컨텍스트를 ~16개로 제한한다. 지도 인스턴스를 여러 개 띄우면 오래된 컨텍스트가 강제로 소실되고("Too many active WebGL contexts"), 그 지도는 멈춘다.

Example 2에서 `WEBGL_debug_renderer_info`로 지금 이 브라우저가 실제로 어떤 렌더러를 쓰는지 확인할 수 있다. Renderer 문자열에 `SwiftShader`나 `llvmpipe`가 보이면 그게 바로 폴백 상태고, 그 환경에서는 회전이 동작하지 않는다.

---

## 정리

| | 회전 처리 | 품질 | 비용 | 라벨 |
|---|---|---|---|---|
| 래스터 | 비트맵 리샘플 (CPU) | 흐려짐 | 픽셀 수 비례 | 같이 기울어짐 |
| 벡터 | 좌표 행렬곱 (GPU) | 항상 선명 | 거의 0 | 빌보드로 수평 유지 |

"지도 회전 지원"은 독립적인 기능이 아니라 **벡터/GPU 렌더링의 부산물**이다. 그래서 GPU가 빠지면 — 블록리스트든, 가속 비활성이든, 컨텍스트 한도든 — 회전이라는 기능 자체가 사라진다. 회전이 필수라면 벡터 렌더링이 가능한 환경을 보장하거나, GPU 가용성을 먼저 감지해 대체 UX를 준비해야 한다.
